# Стратегии развёртывания

Для демонстрации стратегий использовались две версии приложения:

- `api-v1` — образ `habittracker-api:v1`, эндпоинт `/version` возвращает `{"version":"v1.0"}`
- `api-v2` — образ `habittracker-api:v2`, эндпоинт `/version` возвращает `{"version":"v2.0"}`

## Реализованные стратегии

### Rolling Update

Изменение версии внутри одного Deployment. HTTPRoute статичен и всегда смотрит на сервис `api-v1`.


### Blue/Green

Два независимых Deployment (`api-v1` и `api-v2`) живут одновременно. Переключение трафика — изменение `backendRef` в HTTPRoute. Откат — обратное изменение.


### Canary

Один HTTPRoute с двумя `backendRefs` и весами. Трафик распределяется пропорционально весам.

### A/B-тестирование

HTTPRoute с двумя правилами. Первое правило содержит `matches` по заголовку `x-user-group: beta` и направляет такие запросы на `api-v2`. Все остальные запросы на `api-v1`.

### Shadow 

HTTPRoute с фильтром `RequestMirror`. Основной трафик идёт на `api-v1`, копия каждого запроса отправляется на `api-v2`. Ответ от теневой версии игнорируется.
