## Трекер привычек (Habit Tracker)

### Доменная область приложения
   Приложение представляет собой систему для отслеживания формирования полезных привычек. Пользователь может создавать привычки, задавать для них кастомный период выполнения. Система отслеживает факты выполнения, визуализирует прогресс и предотвращает двойное выполнение одной привычки в течение одного дня. При достижении цели привычка отмечается как выполненная и перемещается в конец списка.

### Стек реализации
   Backend: .net 9, ASP.NET Core, EF Core
   Frontend: TypeScript, React, Vite.
   СУБД: PostgreSQL

### Основные сущности доменной области
   ```
   Habit (Привычка):
   {
       Id — уникальный идентификатор
       Name — название привычки
       Period — тип периода оценки
       TargetCount — целевое количество выполнений за период
       CreatedAt — дата создания
   }
   ```

```
   HabitLog (Факт выполнения):
   {
       Id — уникальный идентификатор
       HabitId — внешняя ссылка на привычку
       CompletedAt —  дата выполнения
   }
```

## Как запустить проект

### Вариант 1 (основной): Docker — одна команда
Ни .NET SDK, ни Node, ни PostgreSQL на машину ставить не нужно — всё внутри образов:
```
cp .env.example .env        # один раз: задать конфигурацию и секреты среды
docker compose up --build
```
Приложение: http://localhost:3000 (фронтенд), API: http://localhost:5286/api.
При старте compose сначала запускается одноразовый сервис `migrate` (накат схемы),
и только после его успешного завершения стартует `api`.

### Вариант 2: локальная разработка без Docker
```
# зависимости
dotnet tool restore && dotnet restore backend/backend.sln
npm ci                                   # во frontend/, строго по package-lock.json

# конфигурация — только переменные окружения, файлы с паролями не используются
$env:ConnectionStrings__DefaultConnection = "Host=localhost;Port=5432;Database=habits;Username=postgres;Password=YOUR_PASSWORD"

# схему БД создаёт одноразовый процесс, а не приложение
dotnet ef database update --project HabitTracker.Api --startup-project HabitTracker.Api

dotnet run --project HabitTracker.Api --no-launch-profile   # backend
npm run dev                                                   # frontend
```
> Важно: если БД создавалась старым способом через `EnsureCreated()` (до перехода на
> миграции), в ней нет таблицы истории миграций, и `database update` упадет на
> существующих таблицах. Есть два варианта (оба — один раз):
>
> 1. Проще: сбросить локальную БД и накатить миграции заново
>    `DROP DATABASE habits; CREATE DATABASE habits;` (в Docker — `docker compose down -v`).
> 2. Без удаления данных — «базировать» существующую БД (schema от `EnsureCreated`
>    совпадает с `InitialCreate`), создав историю миграций и накатив только новые:
>    ```sql
>    CREATE TABLE IF NOT EXISTS "__EFMigrationsHistory" (
>        "MigrationId" character varying(150) NOT NULL,
>        "ProductVersion" character varying(32) NOT NULL,
>        CONSTRAINT "PK___EFMigrationsHistory" PRIMARY KEY ("MigrationId")
>    );
>    INSERT INTO "__EFMigrationsHistory" ("MigrationId", "ProductVersion")
>    VALUES ('20261005150209_InitialCreate', '9.0.20');
>    ```
>    затем `dotnet ef database update` (накатится только `AddUniqueDailyCompletion` —
>    уникальный индекс, защищающий от двойного выполнения за день).

## Структура репозитория
```
.env.example                  # шаблон конфигурации среды (без секретов)
.gitignore                    # bin/obj, node_modules, .env, .idea не попадают в репозиторий
.config/dotnet-tools.json     # локальные dotnet-тулы с зафиксированной версией (dotnet-ef)
.github/workflows/ci.yml      # CI: сборка backend, frontend и docker-образов
docker-compose.yml            # единая точка запуска: db + migrate + api + web
backend/HabitTracker.Api/
    Program.cs                        # без секретов и без создания схемы БД
    appsettings.json                  # только нечувствительные настройки (логирование)
    Migrations/                       # схема БД описана кодом миграций
    Dockerfile                        # build-артефакты: runtime и migrate
frontend/
    .env.example                      # шаблон адреса API
    package.json                      # версии зависимостей зафиксированы точно
    Dockerfile, nginx.conf            # сборка UI + проксирование /api
```

## Обоснование соответствия методологии 12 факторов

### 1. Кодовая база
Вся кодовая база хранится в едином git-репозитории: корень — `HabitTracker/`, в нём
`backend/`, `frontend/`, `docker-compose.yml`, `.github/workflows/`. Артефакт —
сам репозиторий и его история коммитов.
Гитхаб - https://github.com/EvgeniaKuskova/sre

### 2. Зависимости
Все зависимости явно задекларированы и изолированы:
* Backend: пакеты NuGet зафиксированы в `HabitTracker.Api.csproj`, локальный тул
  `dotnet-ef` — в `.config/dotnet-tools.json`.
* Frontend: в `package.json` версии зафиксированы **точно** (без `^` и `~`),
  например `"react": "19.3.0"`; воспроизводимая установка — `npm ci` строго по
  `package-lock.json`.
* Изоляция: `node_modules`, `bin/`, `obj/` в репозиторий не попадают (`.gitignore`),
  зависимости ставятся в контейнер (`npm ci`, `dotnet restore`) или в локальное
  окружение разработчика, а не расшариваются между проектами.

### 3. Конфигурация
В коде и в репозитории нет ни паролей, ни адресов. Всё, что меняется между средами,
передаётся переменными окружения:
* `ConnectionStrings__DefaultConnection` — строка подключения к БД (приложение
  завершится с понятной ошибкой, если переменная не задана);
* `PORT` / `ASPNETCORE_URLS` — адрес и порт привязки;
* `VITE_API_URL` — публичный адрес API для фронтенда (в коде нет значения по
  умолчанию, только `import.meta.env.VITE_API_URL`).
`appsettings.json` остался, но в нём только нечувствительные настройки (уровни
логирования). Секреты живут в `.env`, который в репозиторий не попадает — в git
лежит только шаблон `.env.example`.

### 4. Вспомогательные сервисы
PostgreSQL рассматривается как присоединяемый ресурс: сервис `db` в
`docker-compose.yml` поднимается образом `postgres:17-alpine`, а приложение получает
строку подключения из переменной окружения. Смена СУБД или провайдера требует
только изменения `ConnectionStrings__DefaultConnection` — код и образ приложения
не меняются. `appsettings.json` для подключения к БД не используется.

### 5. Сборка, релиз, запуск
Этапы строго разделены:
* **Build** — `docker build` (backend и frontend): установка зависимостей и
  компиляция -> готовый к запуску артефакт (образ). Внутри образа нет ни
  конфигурации среды, ни секретов.
* **Release** — образ «обогащается» конфигурацией конкретной среды: переменные
  окружения из `.env` (локально) или из k8s-манифестов (во 2-й домашке).
* **Run** — `docker compose up`: запуск контейнеров `db`, `migrate`, `api`, `web`.
Проект запускается одной командой без установки .NET SDK, Node и PostgreSQL на
хост. Схему БД создаёт отдельный одноразовый сервис `migrate`, а не веб-сервер
при старте (см. п. 8 и п. 12).

### 6. Процессы
Приложение является stateless (без состояния). Бэкенд не хранит данные пользователей
в оперативной памяти или локальной файловой системе. Всё состояние сохраняется в
PostgreSQL (том `pgdata` в docker-compose). Быстрый горизонтальный масштаб:
число реплик задаёт только среда (во 2-й домашке — k8s), код приложения при этом
не меняется.

### 7. Привязка к портам
Бэкенд-приложение самодостаточно: оно само читает адрес/порт привязки из
переменных окружения (`PORT` или `ASPNETCORE_URLS`) и сообщает об этом в лог.
В коде и в конфигурации приложения портов и хостов нет — в `docker-compose.yml`
порт только публикуется наружу (`API_PORT`), внутри контейнера приложение слушает
`http://+:8080`.

### 8. Параллелизм
Масштабирование достигается за счёт модели процессов: каждый инстанс независим,
состояние не хранится в памяти, поэтому число реплик задаётся окружением
(`--scale api=3`). ASP.NET Core асинхронно обрабатывает входящие HTTP-запросы
(async/await), не блокируя потоки.
Гонки устранены:
* схему при старте больше не создаёт рантайм-инстанс (не было `EnsureCreated()`
  одновременно у 2+ реплик) — это делает одноразовый процесс миграций, плюс EF Core
  берет эксклюзивную блокировку на время наката;
* «отметить дважды за день» закрывается на уровне СУБД: уникальный индекс
  `IX_HabitLogs_HabitId_Day (HabitId, (("CompletedAt" AT TIME ZONE 'UTC')::date))`.
  Проверки read-check-write в коде оставлены для сообщений пользователю, а фактическую
  гарантию дает индекс: конкурентная вставка падает с ошибкой 23505, которую контроллер
  превращает в ответ «Вы уже отмечали эту привычку сегодня».

### 9. Утилизируемость
Процессы спроектированы для быстрого запуска и корректного завершения (graceful shutdown).
При старте приложение только читает конфигурацию и регистрирует сервисы — никакой
работы с БД (инициализация схемы вынесена в одноразовый процесс), поэтому старт
минимальный и предсказуемый. При получении SIGTERM ASP.NET Core дожидается
завершения активных запросов к БД перед закрытием соединений, предотвращая потерю
данных; контейнеры останавливаются через `docker compose stop`/`down`.

### 10. Среды разработки и продакшена приближены друг к другу
Стек один и тот же в обеих средах: те же образы (собираются из тех же Dockerfile),
та же СУБД (PostgreSQL), те же переменные окружения (`ConnectionStrings__DefaultConnection`,
`PORT`, `VITE_API_URL`), один и тот же код миграций. Разница между средами — только
в значениях переменных окружения (`.env` локально, манифесты k8s на проде).
Автоматизация: `docker compose up --build` для локального запуска и CI
(`.github/workflows/ci.yml`), который на каждый push/pull request собирает backend,
frontend и docker-образы — то есть релиз-артефакты проверяются до деплоя;
деплой на k8s настраивается во 2-й домашке.

### 11. Логи
Приложение не пишет логи в локальные файлы. Все события, ошибки и информационные
сообщения записываются в стандартные потоки вывода (stdout/stderr) через встроенный
ILogger ASP.NET Core. В контейнеризированной среде потоки читаются командой
`docker compose logs api`, на проде их собирает централизованный сборщик логов.

### 12 Административные процессы
Управленческие задачи выполняются как одноразовые процессы, а не встроены в цикл
веб-сервера:
* `docker compose run --rm migrate` (или `dotnet ef database update`) — накат схемы;
* `dotnet ef migrations add <Name>` — новая миграция (тул зафиксирован в
  `.config/dotnet-tools.json`, версия воспроизводима);
* сервис `migrate` в compose запускается один раз и завершается — веб-сервер
  схему не создает.
